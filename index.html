ปัญหาจากโลกความจริง

ร้านซ่อมต้องจัดการงานซ่อมหลายประเภทพร้อมกัน — โน้ตบุ๊ก, เดสก์ท็อป, iPhone, มือถือ Android — ซึ่งแต่ละประเภทมีราคา รายละเอียด และขั้นตอนการทำงานต่างกัน การจดในสมุดหรือสเปรดชีตทำให้เกิดปัญหา:

  • งานซ่อมหายและลืมติดตามผล
  • คิดราคาไม่เป็นมาตรฐาน (อุปกรณ์แต่ละชนิดคิดต่างกัน)
  • ไม่มีประวัติลูกค้าหรือช่างเทคนิค
  • ไม่เห็นภาพรวมรายได้ของร้าน

แนวทางของเรา: ออกแบบโมเดล OOP โดยให้อุปกรณ์แต่ละชนิดเป็น ประเภท (type) ที่แตกต่างกันของแนวคิดเดียวกัน — นั่นคือคลาส RepairItem พฤติกรรมร่วมอยู่ที่คลาสแม่ แต่ละชนิดของอุปกรณ์ให้รายละเอียดของตัวเอง

ทำไม OOP ถึงเหมาะกับปัญหานี้:
งานซ่อมเป็น วัตถุ (object) ตามธรรมชาติ (มีสถานะ + พฤติกรรม) อุปกรณ์ต่างชนิดมีโครงสร้างร่วมกัน (Inheritance) แต่มีราคาต่างกัน (Polymorphism) OOP ทำให้ระบบขยายง่าย — การเพิ่ม การซ่อมแท็บเล็ต ในอนาคต = แค่เพิ่มคลาสย่อยอีก 1 คลาส

Abstraction (นามธรรม) — กำหนดข้อตกลงร่วม

แนวคิด: ซ่อนความซับซ้อนไว้เบื้องหลังอินเทอร์เฟซง่าย ๆ คลาส BaseEntity (บรรทัด 13) และ RepairItem (บรรทัด 37) เป็นคลาส นามธรรม — สร้างโดยตรงไม่ได้ ต้องสร้างผ่านคลาสย่อยเท่านั้น คลาสเหล่านี้ประกาศว่างานซ่อมทุกชิ้น ต้องทำอะไร ไม่ใช่ ทำอย่างไร

  • การป้องกันnew.target บล็อกการสร้างคลาสโดยตรงบรรทัด 17
  • ข้อตกลงงานซ่อมทุกชิ้นต้องมี calculateCost(), getDeviceSpecs(), type, displayInfoบรรทัด 50, 53, 56
  • ผลลัพธ์ส่วน UI ไม่ต้องสนใจประเภทอุปกรณ์ — แค่เรียกอินเทอร์เฟซใช้ใน renderer

Encapsulation (การห่อหุ้ม) — ปกป้องสถานะข้อมูล

แนวคิด: เก็บข้อมูลเป็นส่วนตัว เปิดเผยผ่านตัวเข้าถึง (getter/setter) ที่มีการ ตรวจสอบความถูกต้อง ทุกคลาสซ่อนฟิลด์ด้วยเครื่องหมาย #private — ข้อมูลที่ไม่ถูกต้องจะเข้าสู่ระบบไม่ได้

  • ฟิลด์ส่วนตัว#id, #status, #priority, #partsCost, #laborHours…บรรทัด 14, 38–40
  • การตรวจสอบsetter ของสถานะปฏิเสธค่าที่ไม่อยู่ในรายการที่อนุญาตบรรทัด 63–65
  • DataStoreสถานะ + การบันทึก ซ่อนอยู่หลัง API แบบ CRUDบรรทัด 361
  • ผลลัพธ์พิมพ์ผิดเช่น "In Progresss" จะ error แทนที่จะทำให้ข้อมูลเสีย—

63     set status(val) {
64         const allowed = ["Pending", "In Progress", "Completed", "Ready for Pickup", "Cancelled"];
65         if (!allowed.includes(val)) throw new Error(`Invalid status: ${val}`);
66         this.#status = val;
67     }

Polymorphism (พหุสัณฐาน) — คำสั่งเดียวกัน พฤติกรรมต่างกัน

แนวคิด: ชื่อเมธอดเดียวกัน calculateCost() ให้ผลต่างกันตามประเภทจริงของวัตถุ ส่วน UI เรียกเมธอดนี้เหมือนกันกับทุกงานซ่อม — แล้วอุปกรณ์แต่ละชนิดคำนวณราคาของตัวเอง RepairFactory เลือกคลาสย่อยที่ถูกต้องตอนรันไทม์

  • ComputerRepairราคา = อะไหล่ + ชั่วโมง × $40บรรทัด 121–124
  • SmartphoneRepairราคา = อะไหล่ + ชั่วโมง × $30บรรทัด 190–193
  • FactoryRepairFactory.create() คืนคลาสย่อยที่ถูกต้องบรรทัด 504–511
  • UIRenderer เรียก r.calculateCost() — ไม่มี if/else ตามประเภทตาราง/แดชบอร์ด
